# Jewelry Appraisal & Trading Management Web Application

## 1. Project Overview

Build a modern, responsive web application for a jewelry appraisal and purchasing company operating multiple branches across Indonesia.

The application will be used by two primary user groups:

1. **Branch Staff:** Handle customer transactions, photograph jewelry, perform appraisals, present calculated prices, and process payments.
2. **Management:** Monitor branch operations, review staff performance, track transactions and payments, and manage daily jewelry prices.

The application should provide a seamless experience for staff and customers, with a particularly polished interface for presenting jewelry appraisal results to customers.

**Frontend technology:** SolidJS.

For now, focus entirely on the frontend. Implement mock data and mock backend interactions where necessary, but design the application with a realistic backend integration in mind.

## 2. Business Workflow

Each branch has multiple service counters. Every counter is equipped with an iPad used by staff to interact with customers and present appraisal results.

Staff also use an iPhone in the backroom to photograph jewelry during the appraisal process.

The application must support the following workflow:

### Step 1: Customer Arrival

- Staff greet the customer.
- Staff create a new transaction.
- Enter relevant customer information.
- Assign the transaction to the current branch and service counter.
- Generate a unique transaction ID.

### Step 2: Initial Jewelry Registration

The customer brings one or more jewelry items to sell.

For each item:

- Take a photograph of the jewelry using the device camera.
- Allow staff to retake or review the photograph.
- Record the jewelry type or description.
- Add the item to the current transaction.

A transaction can contain multiple jewelry items, each with its own appraisal process.

### Step 3: Backroom Appraisal

Staff take the jewelry to the backroom for assessment.

For each jewelry item, staff must record:

- Weight (grams).
- Purity (e.g., 24K, 22K, 18K, or measured purity).
- Weighing scale photograph.
- XRF machine photograph showing the purity measurement.
- Any additional appraisal notes.

The interface should be optimized for an iPhone, including camera access, touch interactions, and smaller screen layouts.

Staff should be able to switch between the iPad at the counter and the iPhone in the backroom without losing transaction progress.

### Step 4: Price Calculation

Once appraisal data is available, the backend will calculate the purchase price.

For now, simulate this calculation using mock data.

The calculation should be based on:

- Jewelry weight.
- Measured purity.
- Today's gold price.
- Company pricing rules or deductions.
- Any applicable adjustments.

The frontend should display a clear price breakdown for each jewelry item and the overall transaction.

Do not hardcode business pricing rules into the UI. Keep calculation logic behind a mock API abstraction so it can later be replaced with real backend responses.

### Step 5: Customer Presentation

Staff return to the counter and present the appraisal results using the iPad.

This is one of the most important parts of the application.

Create a dedicated customer-facing presentation mode with a polished, premium appearance.

It should display:

- Photograph of each jewelry item.
- Weight.
- Purity.
- Today's gold price.
- Calculated purchase price.
- Price breakdown.
- Total purchase offer.

The presentation should be easy to understand for customers who are not familiar with jewelry valuation.

Include appropriate transitions and visual hierarchy. Avoid making this look like a generic administrative dashboard.

### Step 6: Customer Price Review via QR Code

Generate a QR code containing a temporary public URL for the transaction.

Customers can scan the QR code using their own phones to review their appraisal results independently.

Requirements:

- The URL should be generated by the backend (simulate this for now).
- The URL should be temporary and expire after a configurable period.
- The public page must be read-only.
- Customers must not need to log in.
- The page should display the same appraisal results presented by the staff.
- The interface should work well on mobile browsers.

### Step 7: Payment

If the customer accepts the offer:

- Mark the transaction as accepted.
- Record the payment method.
- Record the payment amount.
- Allow staff to take a photograph of the payment receipt.
- Allow staff to review and retake the receipt photograph.
- Mark the transaction as completed after payment confirmation.

Support appropriate transaction statuses, such as:

- Draft
- In Appraisal
- Awaiting Customer Decision
- Accepted
- Payment Processing
- Completed
- Rejected
- Cancelled

## 3. Cross-Device Synchronization

An important requirement is that staff will switch between devices during a transaction.

For example:

1. Staff create a transaction on an iPad.
2. Staff take jewelry photographs on the iPad.
3. Staff move to the backroom with an iPhone.
4. Staff open the same transaction on the iPhone.
5. Staff record weight, purity, and appraisal photographs.
6. Staff return to the iPad.
7. The updated appraisal information is immediately available.

The backend will eventually own the transaction state and synchronize it across devices.

For the frontend:

- Design the application around persistent transaction IDs.
- Avoid relying exclusively on local component state.
- Implement a centralized transaction/session store.
- Simulate backend persistence.
- Use WebSocket for real-time synchronization if appropriate.
- Alternatively, use another synchronization mechanism if it provides a better architecture.
- Clearly separate API communication from UI components.
- Handle loading, reconnection, and synchronization states.
- Avoid overwriting newer data with stale local state.

The frontend should make it easy to resume an existing transaction from another device.

## 4. Staff Voice Recording & AI Evaluation

The application must also record staff conversations with customers throughout the transaction.

The purpose is to evaluate staff communication quality using AI.

### Live Speech Transcription

Implement client-side live speech transcription in Bahasa Indonesia.

Requirements:

- Capture audio through the device microphone or a dedicated headset.
- Display live transcription as the staff speaks.
- Support Bahasa Indonesia (`id-ID`).
- Send transcription segments to the backend as they become available.
- Associate transcription data with the current transaction.
- Preserve timestamps and speaker/session context where available.

Use an appropriate browser-side speech recognition or transcription library/API.

Do not assume that the browser provides reliable native speech recognition on every device. Keep the transcription implementation behind an abstraction so it can be replaced with another provider if necessary.

### Recording Controls

Staff need explicit controls to:

- Start recording.
- Pause recording.
- Resume recording.
- Stop recording.

Recording should also support automatic pause/resume mechanisms where practical.

For example, staff may temporarily leave the counter and enter the backroom, where the conversation is no longer relevant.

The interface should clearly indicate the current recording state.

### AI Evaluation

The backend will eventually evaluate staff performance based on the transcribed conversation.

For now:

- Send transcription segments to a mocked backend endpoint.
- Simulate AI evaluation results.
- Display evaluation information in the management dashboard.
- Keep the evaluation data model flexible enough to support future criteria such as greeting quality, communication clarity, professionalism, customer engagement, and procedural compliance.

Make recording status and transcription status visible without obstructing the main transaction workflow.

Also provide appropriate microphone permission handling and error states.

## 5. Management Application

Create a separate management interface within the same application.

Management users should have a different experience from branch staff.

### Dashboard

Display an overview of business operations:

- Total transactions today.
- Total purchase value today.
- Total completed payments.
- Number of active transactions.
- Number of customers served.
- Branch performance comparison.
- Staff performance overview.

Use charts and summary cards where appropriate.

### Transaction Management

Managers should be able to:

- View all transactions across branches.
- Filter by branch, staff, date, and transaction status.
- Search by transaction ID or customer information.
- View individual transaction details.
- Review jewelry photographs and appraisal results.
- Review payment information and receipt photographs.
- Review transaction history.

### Staff Performance

Display staff performance based on AI conversation evaluation.

Include:

- Number of customers served.
- Completed transactions.
- Conversion rate (accepted offers vs. rejected offers).
- AI-generated conversation evaluation.
- Evaluation history.
- Transcription review where permitted.

Provide a staff detail page with individual performance metrics.

### Daily Gold Price Management

Managers must be able to configure today's gold prices.

Requirements:

- Set gold prices by purity or karat.
- Display the currently active price list.
- Update prices.
- Maintain price history.
- Record who changed the prices and when.
- Apply changes to new appraisals without unexpectedly modifying completed transactions.

The price management interface should make it clear which prices are currently active.

### Branch Management

Support multiple branches in Indonesia.

Managers should be able to:

- View available branches.
- View branch-level transaction statistics.
- Monitor active transactions.
- View staff assigned to each branch.
- Compare performance across branches.

## 8. Technical Requirements

### Frontend Stack

- SolidJS.
- TypeScript.
- Modern CSS.
- A suitable routing solution.
- A suitable state management approach.
- Reusable components.
- Responsive layouts.

Choose additional libraries where they provide meaningful value, particularly for:

- QR code generation.
- Camera capture.
- Live speech transcription.
- Charts.
- WebSocket communication.

Keep dependencies reasonable.

### Backend Integration

Do not implement the actual backend.

Instead, implement a well-structured mock API layer that represents the future backend contract.

**Important requirements:**

1. Every HTTP request must use a relative URL. Never hardcode a hostname or absolute API URL.
2. Every `fetch()` call must have a descriptive comment explaining the expected backend behavior.
3. Make API requests from a centralized API/service layer rather than directly inside UI components.
4. Use realistic request and response structures.
5. Include appropriate loading, error, and empty states.
6. Simulate asynchronous API responses where necessary.
7. Keep the frontend independent of the mock implementation so the real backend can replace it later.

For example:

```typescript
// Backend: Create a new transaction and return its unique transaction ID.
const response = await fetch("/api/transactions", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
});
```

`/api/ws/transactions/:id`

Use it to synchronize transaction changes between the iPad and iPhone.

Document the expected WebSocket events and payloads.
